你会第二次遇到同一类错误。这不是记性问题——文档不执行，而代码库每天有几百次机会重犯它。所以真正的问题不是"怎么记住"，而是"怎么让它在写错的那一刻就过不去"。

## 优先级链

:::code 从最强到最弱
架构约束   写不出来（结构上不可能）
类型       编译不过
lint       提交不了
CI 检查    PR 红了
测试       回归被抓住
文档       靠人记得读
:::

越靠上越省事：上面的拦住了，下面的就不用写。反过来，只在文档里写规则，等于把执行成本转移给每个人的记忆——而记忆是最不可靠的那一层。

## 升级路径：同一个错犯第二次时

1. 这个错能用结构消灭吗？用联合类型排除的状态、用 brand 分开的值、禁止某个目录 import 某个包——做这个。
2. 结构拦不住的，能不能用一个 lint 规则或 CI 脚本抓？
3. 都不能，才写测试；测试也覆盖不到，才写文档。

:::callout insight 一个简单的判据
你第二次因为同一个原因犯错，说明上次你只写了文档。这不是批评记性，是指出层次选错了。
:::

这条原则也是 pstack 里唯一一条关于"学习本身"的原则。你这 24 条原则要真的长在身上，最终形态大概也是这样——不是记住 24 句话，而是项目里多出几条规则、几种类型、几个检查。

## 结课自测（合上页面再答）

1. 拿到需求，先跑哪三道闸？
2. 想删一段代码，需要什么级别的证据？
3. 同一个坑改了两版还没好，该怀疑什么？
4. 防御该放哪？什么时候加防御算藏 bug？
5. 什么算"做完了"？
6. 报了"快了 10 倍"，要先问哪四个问题？

:::callout task 结课动作（15 分钟）
把这六句话的答案写在一张纸上，不要翻站。答不出来的那一条，回去重读对应那一课——那一条就是你的短板。下周再答一次，只答这一条。
:::

## 检验一下（合上笔记再答）

:::quiz q1
同一条规则，最该落在哪一层？

- [x] 架构与类型约束
- [ ] 团队文档首页
- [ ] PR 模板清单
- [ ] 代码注释顶部

> 越靠上的层次越不依赖人的记忆。结构上写不出来，比文档里写十遍都可靠。
:::

:::quiz q2
什么时候说明上次的教训没有真正落地？

- [ ] 第一次遇到这个问题
- [x] 第二次犯同样的错
- [ ] 文档写得不够长
- [ ] 测试覆盖率不足

> 第二次犯，说明上次只留下了文字，没有留下约束。这是升级层次的信号，不是记性问题。
:::

:::quiz q3
优先级链里，文档为什么排最后？

- [ ] 文档最不好维护
- [x] 文档不参与执行
- [ ] 文档检索不方便
- [ ] 文档总会被写错

> 文档需要有人记得读、记得照做。它把执行成本交给记忆，而记忆不是约束。
:::
