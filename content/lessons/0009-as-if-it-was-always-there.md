焊补丁的典型形态：加一个 flag、加一个可选参数、加一层适配。每一处都不大，但组合起来是一个"只有原作者能改"的结构。重画则是先假装需求一开始就在，把它当成基础假设重新设计一遍。

## 重画三问

1. 如果这个需求第一天就存在，数据会长什么样？
2. 按那个样子重画一遍，再和现实对比，看差在哪一步？
3. 差异通常集中在少数几个类型上——只改那几个，而不是到处加判断。

:::code 同一个需求：单选变多选
// 补丁派：单选结构不动，外面套多选
type Selection = { id: string; extraIds?: string[] };
// 于是每个用到 selection.id 的地方都要问一句：那 extraIds 呢？

// 重画派：一开始就是集合
type Selection = { ids: ReadonlySet<string> };
// 单选 = 集合里恰好一个元素。没有第二种形状，也没有"两个字段要保持同步"。
:::

:::callout insight 关键点
重画的成本不是"重写一遍"，是"想清楚一次"。多数情况下你会发现，需要动的只有类型定义和两三处边界，而不是整个模块。
:::

## 第二部分：最小化读者负担

代码是写给人读的，而读者的工作记忆很小。读者负担有两个可数的来源：从问题到答案隔了几层，以及脑子里同时要装多少隐藏状态。

- 只有一个调用方的包装层：通常可以直接内联，层数 -1，读者少跳一次。
- 可变作用域太大：把变量声明挪到真正需要它的那一行，读者不用记"它前面改过吗"。
- 必须"先知道 A 才知道 B 在干什么"：这是隐式前置知识，能合就合。

:::code 数层数
// 三层：页面 → hook → 仓储 → fetch
useUsers() → repo.listUsers() → http.get('/users')
// 仓储只做转发，没有自己的逻辑 → 内联，两层足够

// 但注意：如果仓储负责了缓存、重试、字段映射，
// 它不是一层包装，是一个真实的边界，别碰。
:::

:::callout warn 别为了"整洁"增加层
层数不是抽象能力，是读者的成本。抽象只有在"它隐藏了真实的复杂度"时才值得——转发式包装藏起来的只有调用栈。
:::

:::callout task 今天做一次（10 分钟）
挑一个"加过三次补丁"的功能，写一句话：如果它一开始就长现在这样，类型会怎么写？然后把这句话和现有类型并排放，看差几个字段。差三个以内，今天就改；差十个，说明该单独排期。
:::

## 检验一下（合上笔记再答）

:::quiz q1
"从第一性原理重设计"的第一步是？

- [ ] 先写一版新实现
- [x] 假设需求本来就在
- [ ] 先补上缺失的测试
- [ ] 先做一次性能剖析

> 先假设需求从第一天就存在，才能看出理想结构是什么样。有了对照，才知道补丁差在哪。
:::

:::quiz q2
什么样的包装层应该内联掉？

- [x] 只有一个调用方的转发
- [ ] 带缓存的仓储层
- [ ] 做字段映射的适配层
- [ ] 处理重试的网络层

> 纯粹转发的包装只藏了调用栈。带缓存、映射、重试的层藏着真实复杂度，不能动。
:::

:::quiz q3
"读者负担"最直接的两个可数来源是？

- [ ] 文件数量与总行数
- [x] 层数与隐藏状态
- [ ] 注释密度与命名
- [ ] 依赖数量与打包体积

> 层数决定读者要跳几次，隐藏状态决定他脑子里要同时装几件事。这两个都能数出来。
:::
