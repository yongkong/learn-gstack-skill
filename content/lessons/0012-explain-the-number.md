"快了 10 倍"是最常见的一种。它可能是真的：那一段确实快了一百倍。但如果那一段只占端到端时间的 0.5%，用户完全感觉不到——你优化了 0.5%，汇报了 10 倍。

## 盘问四问

1. 是什么限制了它？现在的数字是被目标本身限制，还是被某个次级瓶颈限制（I/O、GC、网络、锁）？
2. 它覆盖了端到端吗？还是只测了好测的那一段？
3. 方差多大？重复跑三次，结果稳定吗？
4. 单位对不对？毫秒和微秒、中位数和平均值、冷启动和热路径。

:::code 一个可疑的比较
before: 4200ms
after:  380ms          → "11x faster"

追问：
1. before 是冷启动（含 JS 编译），after 反而命中了缓存
2. 计时只包住了渲染，没含数据请求
3. 只跑了一次

重测（各 5 次、清缓存、含端到端）：
before: 4180 / 4210 / 4175 / 4200 / 4190   → 中位 4190
after:  1990 / 2010 / 1985 / 2000 / 1995   → 中位 2000
结论：约 2.1x，瓶颈在数据请求，渲染已不是主要成本
:::

:::callout insight 一个合格的结论长什么样
"它现在被 X 限制，所以除非 X 变了，再优化 Y 不会有明显收益。" 这句话比"快了 N 倍"有用得多——它告诉别人下一步该往哪走，以及什么时候该停。
:::

:::callout warn 单次结果不是结论
任何只跑了一次的测量都是噪声。尤其是优化类工作：第一次跑通常包含编译、预热、缓存填充，它测的是"启动"，不是"稳态"。
:::

这条原则的适用面比性能更宽：覆盖率 90%、评测提升 3 个点、失败率降到 0.2%——都是同一个问题：这个数字限制了谁、代表了什么、换个条件还在不在。

:::callout task 今天做一次（10 分钟）
找一个你最近汇报过或相信过的数字，用四问检查一遍。最可能的收获是发现它少了"重复三次"这一步——而这往往会把结论从"10 倍"改成"2 倍"，或者干脆改成"没变化"。
:::

## 检验一下（合上笔记再答）

:::quiz q1
汇报一个加速比之前，必须能说清什么？

- [ ] 用了哪个工具测
- [x] 是什么限制了它
- [ ] 代码改了多少行
- [ ] 谁评审了这次改动

> 知道限制在哪，才知道这个数字能推广到哪、什么时候会失效。这才是别人真正需要的信息。
:::

:::quiz q2
只跑一次的测量最可能的偏差是？

- [ ] 把稳态当成启动
- [x] 把启动当成稳态
- [ ] 单位换算写错了
- [ ] 样本数量太多了

> 第一次跑包含编译、预热、缓存填充。它测的是启动成本，不是长期表现。
:::

:::quiz q3
优化了只占端到端 0.5% 的一段，会发生什么？

- [ ] 端到端时间显著下降
- [x] 局部数字变大总收益小
- [ ] 整体性能反而会变差
- [ ] 无法测出局部改进

> 局部 10 倍可能只换来端到端 5% 的改善。数字没有错，错的是把它当成整体收益。
:::
