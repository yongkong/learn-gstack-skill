## 一、守住上下文窗口

把两千行日志、整个目录、几百行 diff 直接贴进对话，看着是"给足信息"，实际是把后面的判断都放进了噪音里。上下文是有预算的，花在原始材料上，就没钱买结论了。

:::code 同一件事，两种喂法
差：把 3000 行 CI 日志贴进主线程，然后问"为什么挂"
→ 主线程从此背着 3000 行，后面每个判断都在噪音里做

好：派一个子 agent 读完日志，回报三行
→ "挂了 3 个用例，都是 timeout；根因是本地没起 redis；日志在 ci-1234.log"
→ 主线程只背这三行，原始文件留在磁盘上，需要时按路径再取
:::

- 先问自己"我要的是结论还是材料"。要结论，就派出去提炼。
- 主线程只保留可决策的信息。
- 原始材料落盘，用路径引用，不贴进上下文。

## 二、不要阻塞在人身上

另一类浪费是节奏：每次准备动手前先停下来问一句"要我开始吗"。人不在，进度就停在那里——而大多数事情是可以先做、再由人事后纠偏的。

:::code 一张判断表
可逆（做错了能撤回）           → 直接做，做完报告
  改一个函数、加一个测试、重命名

不可逆（做错了收不回）         → 先问
  删数据、发外部消息、部署、改远端分支、调线上配置
:::

:::callout insight 关键点
把选择权留给人，但别把进度也交出去。区别在于：你交出去的是"要不要采用我的结果"，而不是"要不要我开始"。
:::

这两条原则是同一个硬币的两面：一条管信息怎么流动，一条管决策怎么流动。都是为了让"人"这个瓶颈不要卡在中途——人最该出现的地方是开头说清目标、结尾判断结果。

:::callout task 今天做一次（8 分钟）
回看你最近一次"贴了一大段日志"的对话。如果把那段日志换成一封三行摘要，你会问的问题会有不同吗？另外，回忆一下你最近几次停下来问人的事，哪些其实是可逆的。
:::

## 检验一下（合上笔记再答）

:::quiz q1
把大段原始日志贴进主线程的主要代价是？

- [ ] 占用磁盘与内存
- [x] 后续判断被噪音干扰
- [ ] 日志格式无法解析
- [ ] 模型无法读取长文本

> 上下文是有预算的。材料占满了，结论就放不进来，而你后面每个判断都在噪音里做。
:::

:::quiz q2
下面哪件事应该先问再做？

- [ ] 给函数重命名
- [ ] 补一个缺失的测试
- [x] 删除生产数据
- [ ] 调整本地配置

> 判据是"能不能撤回"。删除生产数据不可逆，其余的做错了都能改回来。
:::

:::quiz q3
"不要阻塞在人身上"到底交出去的是什么？

- [x] 对结果的采用权
- [ ] 对进度的控制权
- [ ] 对代码的审查权
- [ ] 对目标的定义权

> 人保留的是"要不要采用这个结果"。如果把进度也交出去，你就把等待变成了默认状态。
:::
