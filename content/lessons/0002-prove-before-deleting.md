代码库会变成沉积岩，不是因为有人喜欢留垃圾，而是因为没人为"它还活着吗"这件事负责。谁也不敢删，因为它可能还有人用；谁也没空验证，因为验证看起来比重写还贵。于是每一层都留着。

## 删除是三件事，不是一件

1. 找出全部引用：静态搜索 + 动态引用。
2. 判断每个引用是否还需要这个行为。
3. 不需要的删掉；还需要的，先把行为搬到新位置。

大多数人直接做第三步，跳过前两步——于是"删除"变成了一次赌。赌赢了省 200 行，赌输了线上少一个功能。

## 静态引用好找，动态引用才是坑

:::code 把搜索范围收紧到"可疑子集"
rg -n "formatRunStatus" --type ts
rg -n "run-status"            # 样式名、i18n key
rg -n "runStatus|run_status"  # 命名风格不一致的残留
rg -n "formatRun" --glob '!**/*.test.ts'
:::

:::callout warn 搜不到，不等于没人用
字符串拼出来的类名、路由表里的字符串、配置里的名字、另一个包里的旧拷贝——这些都不在普通搜索的结果里。搜索只覆盖"名字被原样写出来"的引用。
:::

## 中证据也是证据

如果某条路径你判断不了，就删掉它，然后跑测试。测试红了，说明这个行为还被需要——但这不是"不能删"，而是"删之前先把行为搬到新位置"。删的是实现，不是行为。

:::callout insight 三个证据等级
强证据：搜出全部引用并逐个确认不需要。中证据：有测试覆盖这条路径，删完立刻知道。弱证据：注释掉观察一周、感觉没人用、AI 说它冗余。只有强证据允许直接删，其余两种只允许"先搬再删"。
:::

:::callout task 今天做一次（10 分钟）
挑一个"你一直不敢删"的文件。不要删任何东西，只做第一步：搜出它的全部引用，列成一张表。看看这张表有多长——长度本身就是答案。
:::

## 检验一下（合上笔记再答）

:::quiz q1
删除一段代码前，唯一够格的证据是？

- [ ] 注释掉观察一段时间
- [x] 搜出全部引用并确认
- [ ] 让 AI 判断是否冗余
- [ ] 看它有没有测试覆盖

> 引用清单是别人能复现的工件。观察、感觉、AI 判断都不可复现，也就不能作为证据。
:::

:::quiz q2
下面哪种引用最容易被普通搜索漏掉？

- [ ] 直接 import 后调用的函数
- [x] 字符串拼出来的类名
- [ ] 有类型标注的函数参数
- [ ] 被导出的常量值

> 动态拼接的名字在源码里不是原文，静态搜索找不到。路由表、i18n key、配置键都属这一类。
:::

:::quiz q3
删掉某条路径后测试红了，正确反应是？

- [ ] 立刻回滚并放弃删除
- [ ] 把测试改成跳过该用例
- [x] 先把行为搬到新位置再删
- [ ] 认为测试本身写错了

> 测试红说明行为还被需要。要删的是实现，不是行为——先把行为接上，再删旧实现。
:::
