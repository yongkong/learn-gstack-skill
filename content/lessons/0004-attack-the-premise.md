两次修复往往共享同一个没被说出口的假设："这个字段一定有值"、"这个请求只会发一次"、"这段回调一定在主线程"。修补在假设之内做优化；假设本身错了，再修十次也一样。

## 怎么攻击前提

1. 把前两次修复各自"相信了什么"写成一句话，找出共同的那条。
2. 用一个最小实验直接验证它，而不是在它之下继续改代码。
3. 前提错了就换前提；前提对了，再谈修法。

:::code 真实 bug 里最常见的四类前提
数据：这个字段在这个阶段一定有值
时序：这个请求只会发一次，回调一定按序到达
位置：这段代码一定跑在主线程 / 一定只在一个进程里
共享：这两个地方不会同时写同一份状态
:::

:::callout warn 最强的信号
连续两次在同一道关卡上失败。第三次还按原思路改，你只是在给那个假设加置信度——顺便让下一次排查更难，因为现在有三层补丁。
:::

:::callout insight 为什么 AI 特别需要这条
默认行为是在你给的方向上更努力：加日志、加判断、加重试。它很少说"你这个问题问错了"。攻击前提本质上是允许自己说"我一开始就理解错了"。
:::

注意攻击前提不是更聪明的调试技巧。它是一个动作顺序的调整：把"再修一次"换成"先证伪那个共同假设"。而且它通常更便宜——一个最小实验往往三行代码。

:::callout task 今天做一次（10 分钟）
找一个你改了两次还没好的问题。写下这两次修复共同的假设，然后设计一个能直接证伪它的最小实验。先跑实验，别写第三次修复。
:::

## 检验一下（合上笔记再答）

:::quiz q1
"攻击前提"应该在什么时候触发？

- [ ] 第一次修复失败之后
- [x] 两次修复都失败在同一关
- [ ] 代码评审提出异议时
- [ ] 测试覆盖率低于阈值时

> 一次失败可能是修得不好；两次共享前提的失败才是信号。触发条件写得很严，是为了不被滥用成"遇事就重构"。
:::

:::quiz q2
攻击前提的第一步是？

- [x] 写出前两次共同相信的假设
- [ ] 加更多日志来定位问题
- [ ] 回滚到上一个可用版本
- [ ] 请另一个模型重新修一遍

> 前提没被写下来，就无法被验证。写下来的那一刻，你才能看出两次修复其实在做同一件事。
:::

:::quiz q3
连续两次修复失败，第三次最该做的是？

- [ ] 换一种修复思路再试
- [ ] 扩大这次改动范围
- [x] 直接验证那个共同前提
- [ ] 补齐更多回归测试

> 换思路仍然在同一个前提内。先证伪前提，才知道要不要换掉整个问题。
:::
