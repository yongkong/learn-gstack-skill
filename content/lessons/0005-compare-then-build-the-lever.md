## 第一部分：穷尽设计空间

两条路都说得通、谁也说服不了谁的时候，继续讨论是在消耗时间而不产生信息。原型的作用是把讨论换成一个可观察的事实：做出来，看一眼，你就知道了。

1. 每个原型只为一个判断服务——做之前先写"它能回答哪个问题"，答不出来就别做。
2. 明确写在纸上：这个原型会被扔掉，不进主干。
3. 比较时用同一组输入、同一个标准；否则两个原型各夸各的，等于没比。

:::code 原型判定表（做之前先填）
原型 A：直接渲染 5000 行 markdown
  回答的问题：卡顿是渲染造成的，还是解析造成的？
原型 B：只解析不渲染，计时
  回答的问题：解析本身要多久？

判定标准：同一条 5000 行文档，首屏可交互时间
结论用途：决定要不要上增量解析
:::

:::callout insight 关键点
原型是消耗品，不是草稿版产品。一旦你开始给原型加错误处理、加样式，它就不再是原型，而是一个没经过设计的实现。
:::

## 第二部分：造杠杆

同一件事你要做第二遍，就是在交税。造杠杆的意思是：把这件事变成一个可以重跑的东西——codemod、脚本、生成器，或者一个 agent 能照着执行的 skill。

关键在于"工具是交付物"。你说"我改完了"，对方只能相信；你交一个能重跑的脚本，对方可以自己验证。同一次工作，产出两种东西：结果，以及证明结果的能力。

:::code 手工 vs 杠杆（同一件迁移工作）
手工：在 37 个文件里逐个把 fetchUser 换成 getUser
→ 交付物 = "我改好了" + 一个巨大的 diff

杠杆：写一个 40 行的 codemod，跑 37 个文件
→ 交付物 = 脚本 + 干净 diff + 跑第二遍没有变化
:::

:::callout warn 注意
造杠杆也有成本，别为一次性的小事写工具。判据是：这件事会不会再来一次，或者别人需不需要能重跑它。两个都不满足，手工反而更省。
:::

## 两条原则的共同点

原型是"用低成本换信息"，杠杆是"用一次性成本换重复劳动"。都是把成本挪到前面，让后面的每一步更便宜、更可验证。

:::callout task 今天做一次（15 分钟，二选一）
A：挑一个你纠结了两天以上的技术选择，各花 30 分钟做两个粗糙原型，只回答一个问题。B：挑一件你这周做过第二遍的事，把它写成一个能重跑的脚本，哪怕只有 20 行。
:::

## 检验一下（合上笔记再答）

:::quiz q1
做原型之前必须先确定什么？

- [x] 它能回答哪个问题
- [ ] 它的代码结构分层
- [ ] 它的性能优化方案
- [ ] 它的上线时间点

> 原型的存在意义是产出一个判断。说不出它回答什么问题，它就会变成"没有设计的实现"。
:::

:::quiz q2
什么时候值得造工具，而不是手工做完？

- [ ] 任务看起来很枯燥时
- [x] 这件事会再来一次时
- [ ] 用户明确要求工具时
- [ ] 团队人数比较多时

> 判据是"会不会再来一次"或"别人需不需要能重跑它"。两个都不满足，手工更省。
:::

:::quiz q3
为什么说"工具才是交付物"？

- [ ] 因为工具比改动更容易写
- [ ] 因为代码量越大越显专业
- [x] 因为别人能重跑它来验证
- [ ] 因为工具可以重复卖给客户

> 结果可以被声称，工具可以被重跑。能重跑，评审的人就不必相信你，他自己能验。
:::
