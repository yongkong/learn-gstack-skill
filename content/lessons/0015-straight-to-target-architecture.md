## 一、直线奔向目标架构

多阶段重构最常见的失败方式不是改坏了，而是"改到一半先这样"。为了中间状态能跑，加一层兼容；为了兼容，再分出一个分支。最后三套代码同时活着，谁也不敢删。

:::code 同样的迁移，两种走法
绕路派：老接口 → 适配层 → 新接口 → 老接口的调用点慢慢迁
  第 2 周：适配层上线
  第 5 周：还在迁，适配层有了三个特例分支
  第 9 周：没人记得为什么要适配了

直线派：定好阶段，每阶段一个可验证快照，不留兼容层
  阶段 1：新类型 + 边界写新数据    验证：真实入口跑通
  阶段 2：读路径迁完                验证：数据一致
  阶段 3：删旧路径                  验证：搜索无残留
:::

:::callout warn 那句最贵的话
"先这样，以后重构"——以后几乎从不发生。兼容层不是进度，是给未来开的支票，而且通常没人来兑现。
:::

注意"直奔目标"的前提是阶段边界清楚，每阶段有验证。没有阶段划分的"一步到位"不是这条原则，是一次赌博。

## 二、体验优先

在"实现方便"和"用户爽"之间，默认选后者。这句话听上去像口号，落到具体取舍上却很硬：一个功能做糙了，成本不在开发工时，在用户对你的信任。

:::code 同一周的工作量，两种分法
铺开派：5 个功能都做了 60%
→ 每个都能点，每个都不好用，用户记住的是"都不太行"

收敛派：2 个功能做到 95%，3 个先不做
→ 用户记住的是"这两个真好用"
:::

:::callout insight 关键点
少而精致不是审美偏好，是资源分配策略：用户的印象由最差的那次体验决定，而删掉三个半成品是免费的。
:::

两条原则的连接处在于"不要为省事付长期账"：兼容层是把复杂性推给未来，粗糙功能是把不信任推给用户。两者都是当下省力、之后加倍偿还。

:::callout task 今天做一次（8 分钟）
查一下你代码里有多少处以"兼容""过渡""旧版"为名的分支或文件。挑一个，回答两个问题：它真的还有调用方吗？如果现在删掉，谁会坏？答不上来，它就是那张没人兑现的支票。
:::

## 检验一下（合上笔记再答）

:::quiz q1
多阶段重构里，兼容层的本质是什么？

- [ ] 保证平滑过渡的必要成本
- [x] 把复杂性推迟到未来
- [ ] 一种更稳妥的工程规范
- [ ] 减少测试工作量的手段

> 它让今天少痛一点，代价是未来三套代码并存。而"未来"通常没人清理。
:::

:::quiz q2
"直奔目标架构"的前提条件是？

- [ ] 团队人数足够多
- [x] 阶段边界清楚可验证
- [ ] 有完整的自动化测试
- [ ] 改动规模足够小

> 没有阶段划分的一步到位是赌博。每个阶段有可验证快照，才叫直线前进。
:::

:::quiz q3
粗糙功能真正的成本是？

- [ ] 开发工时的浪费
- [ ] 后续维护的难度
- [x] 用户对产品的信任
- [ ] 测试用例的数量

> 用户的印象由最差体验决定。砍掉三个半成品，比把五个都做到 60% 更划算。
:::
